# 排班表增量同步模拟台

纯前端（原生 ES Module，无构建、无登录态）实现的增量同步协议演示，位于
`frontend/src/sync/`，页面入口 `frontend/sync.html`（路由 `/sync.html`，
nginx 另将 `/sync` 302 到该页）。Node 侧协议测试在 `test/sync.test.js`。

## 要解决的问题

排班表必须跟上「最新估算」。已完成估算的待审工单按**工单号**发增量，
增量只有三类：

| 操作 | 含义 | 记录内容 |
|---|---|---|
| `UPSERT` | 新增或改值 | 工单号、版本号、估算分钟 |
| `RETRACT` | 撤回（退出排班） | 工单号、版本号，分钟为空 |

约束与对策：

- **逐单版本号单调递增**。收件方按工单号记录 `applied_version`，
  `version <= applied_version` 的记录一律丢弃——乱序的旧记录盖不掉新版，
  被撤回的工单也不会被迟到的旧 `UPSERT` 复活。
- **分批收包**。上批没收齐不影响新批发布；包可任意拆分，收件方逐单去重。
- **重试不重复入表**。发送方用 outbox 登记每条记录，重发永远复用同一个
  `record_id`/`version`，绝不重新生成版本；收件方对同版本重复投递返回
  `duplicate` 且不改变表内容。
- **发出未确认 ≠ 未入表**。回执可能丢失而记录已生效，因此补发只针对仍
  `pending` 的记录；另提供「按逐单实收对账」：收件方回报各单已应用版本，
  在途但实际已入表的项直接确认，无需重发。
- **断网恢复**。断网期间数据包挂起不丢；恢复后挂起包继续投递，再按逐单
  实收补发未确认项。
- **同步完成判定**。把排班表与最新估算的规范集合（应排工单 + 分钟数）
  做 diff，`missing / wrong / extra` 全为空才算同步完成；回执是否收齐
  单独展示，不影响表的正确性判定。

## 模块结构

```
frontend/src/sync/
├── engine/
│   ├── store.js       估算事实源：发布 UPSERT/RETRACT，逐单版本号与台账
│   ├── sender.js      发送方 outbox：打包、逐单回执、按实收版本对账
│   ├── receiver.js    收件排班表：版本去重应用、撤回删除、规范集合 diff
│   ├── transport.js   模拟传输：断网挂起、丢包/丢回执、乱序延迟、手动收包
│   └── simulator.js   编排：派生逐单状态（未发布/在途/待补/已生效待回执/已同步）
├── main.js            页面渲染与交互
├── boot.js            挂载入口
└── sync.css
```

记录与回执均为自描述 JSON，例如：

```json
{ "record_id": "QJ-N02#v3", "job_id": "QJ-N02", "version": 3,
  "op": "UPSERT", "estimated_minutes": 230, "title": "校园口述史访谈" }
```

## 页面能做什么

- 顶部展示同步完成判定：应排/实排单数、待确认回执数、待补与待撤回清单。
- 「逐单状态」表：每单最新版本、表内版本、分钟数与五态标记；
  另列出**已生效**与**待补**工单。
- 「估算侧操作」：对任一工单发布改值 `UPSERT`、`RETRACT`，或完成
  `QJ-N04` 的首次估算（演示「未完成估算不发布」）。
- 「网络模拟」：切换在线/断网、调整丢包与丢回执概率、开启乱序延迟、
  手动恢复网络。
- 「发件出口」：全量打包、勾选分包、断网恢复逐单补发、按实收对账、重置。
- 「模拟收包」：对在途/挂起/延迟的数据包手动立即到达，观察逐单应用结果。
- 「事件流」：发包、到达、应用结论（applied/stale/duplicate）、回执、
  对账全部留痕。

## 测试

```bash
node --test test/sync.test.js
```

覆盖：增量类型与版本递增、乱序拒绝旧版、撤回后拒绝复活、重复投递幂等、
断网挂起与恢复补发、回执丢失后对账、分批收包的待补清单、五态状态机、
重置复位。
